CH. 03 / The central skill

03 Code review studio

It ships. But is it right?

Anyone can generate code that looks finished. The valuable move is to slow down, trace what it actually does, and decide whether it belongs. That is the skill this course is built around.

01 The method

The five-pass review.

Use the same questions whether the author was a person, a tutorial, or a language model. Read for intent first; syntax can wait.

Rule of thumb: if the code is short enough that you skip the review, it is short enough to read twice.
  1. 01

    Read the brief

    What was this code supposed to do? Start with intent, not line one. A correct implementation of the wrong requirement is still a defect.

  2. 02

    Trace the data

    Find where input enters, where it is stored, and where it reaches the page. Every input you did not create is a trust boundary until proven otherwise.

  3. 03

    Test the edges

    Empty, very long, duplicated, slow, offline, malicious. The demo path is the easiest path; the bugs live at the edges of it.

  4. 04

    Check the human path

    Tab through it. Zoom the text. Turn off animations. Does focus make sense? Can a screen reader tell what changed? Does it work on a small phone?

  5. 05

    Ask what is missing

    No error state, no loading state, no empty state, no keyboard escape, no explanation. Absence is a finding — often the most important one.

03 Working with AI

Ask better. Then check harder.

AI output is a draft with good manners. A precise prompt narrows the gap between plausible and correct; a review is still what closes it.

A prompt is a specification, not a wish.
01

Name the goal

Describe the user, the page, and the outcome. One feature at a time beats an entire website in a single request.

"Build a keyboard-accessible mobile navigation for a four-page portfolio."
02

State the constraints

Say what cannot change: the existing markup, the supported browsers, the size budget, the design system, the technology you are learning.

"Use HTML, CSS, and vanilla JS. Do not add dependencies. Keep the current nav links."
03

Define acceptance

Write the checks before the code exists. Keyboard, focus, empty, error, narrow screen, reduced motion. This is also the review checklist.

"Works at 360px. Escape closes. Focus returns to the toggle. No layout shift."
04

Ask for the assumptions

Make uncertainty visible. Ask what the model is unsure about, what it chose not to do, and which behaviour it could not verify.

"List your assumptions and the edge cases you did not handle before showing the code."

04 Apply it

Build something. Then review it like it is not yours.

The project brief gives you a real site to practise on. The review habits are what turn a working draft into work you can defend.
