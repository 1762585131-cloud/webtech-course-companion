01 Glossary

Speak the language.

Definitions you can use in a sentence — not a textbook. Search by term, symptom, or idea.

Showing all 20 terms.

URLFoundations
The address of a resource on the web: scheme, host, path, and optional query and fragment. https://site.dev/work?ref=home#process
DNSFoundations
The domain name system — the web's address book. It resolves a name like example.com into an IP address the network can route to.
HTTPFoundations
The request–response protocol browsers and servers use to exchange resources, headers, and status codes. HTTPS is HTTP carried over an encrypted connection.
Status codeFoundations
A three-digit summary of an HTTP response: 2xx success, 3xx redirect, 4xx client error, 5xx server error. A 404 is a valid response, not a crash.
DOMFoundations
The browser's live, tree-shaped representation of the HTML. JavaScript reads and changes the DOM; the source file stays unchanged behind it.
Semantic HTMLHTML
Choosing elements for what content is — heading, nav, main, button, label — not just how it looks. Semantics give browsers, assistive technology, and search engines usable structure.
AccessibilityHTML
Designing so people with different senses, devices, and abilities can use the page. It usually starts with correct HTML, visible focus, and keyboard access.
Form validationHTML
Checking input before accepting it. Browser validation improves the experience; it is never a security boundary. Validate again wherever the data is actually processed.
The cascadeCSS
The algorithm that decides which CSS declaration wins when several rules set the same property. Origin, specificity, and source order all matter.
SpecificityCSS
A weight given to selectors in the cascade. IDs outweigh classes; classes outweigh elements. Reaching for !important usually hides a structural problem.
Box modelCSS
Every element is a content box surrounded by padding, border, and margin. Misunderstanding which part a width applies to is a classic layout bug.
Flexbox & GridCSS
Flexbox distributes items along one axis; Grid works in rows and columns at once. Both are layout tools, not replacements for sensible markup.
Responsive designCSS
A layout that adapts to viewport, content, and capability — not one fixed design squeezed to fit. Fluid widths and content-driven breakpoints come before decoration.
GitShip
A version control system that records snapshots of a project. Commit small changes with messages that explain why, not just what changed.
DeploymentShip
Publishing built files to a host so they are available at a public URL. Test the deployed copy: localhost and production are different environments.
SEOShip
Search engine optimisation: helping crawlers understand genuinely useful content. Clear structure, titles, links, and performance matter more than tricks.
HTTPSSecurity
HTTP over TLS: encrypted in transit and authenticated by a certificate. It protects data between browser and server, not from a compromised or dishonest server.
XSSSecurity
Cross-site scripting: attacker-controlled input becomes executable markup or script in a page. Escape output for its context and avoid sinks like innerHTML for untrusted text.
CSRFSecurity
Cross-site request forgery: another site causes the browser to send an authenticated, state-changing request. Defences include CSRF tokens, SameSite cookies, and Origin checks.
Password handlingSecurity
Passwords need slow, salted hashing and a secure recovery path. A static site should use a trusted authentication provider rather than inventing its own credential storage.

02 Before publish

The ten-minute pre-flight.

Not a substitute for real testing. The minimum pass before you call a site live and send the link to someone who matters.

  • ✓
    Every path resolves.

    Click every link, asset, and nav item on the deployed site — not just locally.

  • ✓
    Headings make sense.

    One h1 per page, no skipped levels, and headings that describe the content beneath them.

  • ✓
    Images have a purpose.

    Useful alt text for content images; an empty alt for decoration. No filenames as descriptions.

  • ✓
    The keyboard works.

    Every interactive element is reachable and operable; focus is visible; nothing traps the user.

  • ✓
    The phone pass.

    Test at 360 pixels on a real device. No horizontal scroll, no tiny tap targets, no hover-only actions.

  • ✓
    Forms explain themselves.

    Visible labels, errors announced and linked to their fields, and a clear confirmation after success.

  • ✓
    No secrets in the repo.

    No passwords, API keys, or private data. Git history is public far longer than you expect.

  • ✓
    Live details are handled.

    HTTPS, correct page titles, a favicon, a useful 404 page, and a working custom domain if you use one.

  • ✓
    The basics are fast.

    Compress images, lazy-load below-the-fold media, and remove scripts or fonts you do not actually use.

  • ✓
    Read it as a stranger.

    Open the homepage cold. Can you tell who it is for and what to do next within ten seconds?

03 Security

The short security brief.

Enough to design safer defaults and ask better questions. Not enough to make you a security engineer — and that is fine.

01 / Default

HTTPS, always.

Serve every page over HTTPS. Modern hosts make certificates straightforward; there is no good reason for a public site to ship without it.

02 / Credentials

Do not store plaintext passwords.

Never store passwords in a repo or a database as plain text. Use a trusted authentication provider, slow salted hashing, and a careful recovery flow. Do not invent cryptography.

03 / Injection

Treat input as hostile.

Do not interpolate untrusted values into HTML. Use textContent when you mean text; sanitise deliberately when you truly need HTML. Avoid inline event handlers.

04 / Requests

Know the CSRF pattern.

State-changing requests need protection: SameSite cookies, CSRF tokens, and Origin checks. Your static project may not have sessions, but the boundary is still worth understanding.

A useful habit: ask “who controls this value, and where does it end up?” on every line that handles input. Most web vulnerabilities are a failure to answer that clearly.

04 The toolkit

Keep these close.

A short list of references worth bookmarking. Start with the docs, then validate what you made.

  • 01 Full lesson material webtech.landrock.io The complete lessons this companion site supports. Start here for the long version of every module.
  • 02 MDN Web Docs developer.mozilla.org The reference for HTML, CSS, JavaScript, and browser APIs, with examples you can inspect.
  • 03 web.dev Learn web.dev/learn Structured learning paths for HTML, CSS, JavaScript, accessibility, and performance.
  • 04 W3C Markup Validation Service validator.w3.org A second pair of eyes for document structure. A pass is not proof of accessibility, but a failure is worth reading.
  • 05 WAVE wave.webaim.org Fast accessibility checks. Combine the output with real keyboard testing and, ideally, a screen reader.
  • 06 Lighthouse developer.chrome.com Performance, accessibility, and SEO signals in Chrome DevTools. Use it to find questions, not to chase a perfect score.
  • 07 Pro Git git-scm.com/book A clear, free book on what Git is actually tracking. Chapters 2 and 3 cover most of what the project needs.
  • 08 GitHub Pages docs.github.com/pages Static hosting directly from a repository — a practical way to satisfy the live URL requirement.
  • 09 Can I use caniuse.com Browser support tables for modern CSS and JavaScript features. Check the feature, not the vibe.
